# NL2SQL 정확도 개선 기록

로컬 소형 LLM(Qwen3-8B, LM Studio)으로 한국어 질문을 MySQL 쿼리로 바꾸는 기능을, **모델을 바꾸지 않고** 어디까지 끌어올릴 수 있는지 측정하며 개선한 기록이다.

## 요약

| 문항 세트 | 시작 | 최종 | 실행 가능률 (최종) |
|---|---|---|---|
| 별도 작성 세트 (`cases_holdout.json`, 25문항) | 65.3% | **80.0%** | 92.0% |
| 개발용 세트 (`cases.json`, 29문항) | 87.4% | **89.7%** | 100% |

- 정확도는 **실행 결과 일치** 기준이다. SQL 문자열이 아니라 실행한 결과를 정답 SQL의 결과와 비교한다.
- 별도 작성 세트의 80.0%에는 질문을 잘못 이해했는데 답이 우연히 같았던 H25(3회)가 들어 있다. 이를 빼면 **76%**다.
- 효과가 컸던 순서: 데이터 정리 → 프롬프트 규칙(동률 처리) → 생성 SQL 정적 검사와 오류 안내.
- 사고 모드와 스키마 값 목록 힌트는 측정해 보니 이득이 없어서 기본값에서 뺐다.
- 남은 오류는 대부분 **질문을 잘못 이해하는** 유형이다. 같은 모델로는 한계에 가깝다고 판단했다.

## 시스템 구성

```
질문 ─▶ 스키마 프롬프트(DDL + 샘플 3행) ─▶ LLM ─▶ SQL
                                              │
                    ┌─────────────────────────┘
                    ▼
        검증: 정적 검사 + EXPLAIN + 질문 값 누락 검사
                    │ 문제 발견 시
                    └─▶ 문제를 되먹여 재생성 (최대 2회)
```

- **정적 검사** (`validate_sql`): WHERE 안의 집계 함수, FULL OUTER JOIN, 플레이스홀더, 상대 테이블에 없는 행을 찾는 쿼리(anti-join)의 잘못된 모양
- **EXPLAIN**: 쿼리를 실행하지 않고 MySQL에 문법·컬럼 오류를 물어본다. 자주 나오는 오류(1055)에는 고칠 방법을 한국어로 덧붙인다.
- **값 누락 검사**: 질문에 나온 숫자나 DB 값(예: '네트워크장비')이 SQL의 리터럴에 없으면 의심 사항으로 되먹인다.

## 평가 방법

- `python -m nl2sql_eval.run_eval --cases <파일> --runs 3 --value-check`
- 문항마다 3회 반복하고, 재생성은 최대 2회 허용한다.
- 정답을 관대하게 보는 것: 컬럼 순서, 별칭, 정답에 없는 컬럼이 더 붙은 것, 값 표기 차이(`'185'`와 `185`)
- 엄격하게 보는 것: 행 수, 각 행의 값, 순서를 요구한 문항의 순서

### 별도 작성 세트를 만든 이유

개발용 세트(`cases.json`)는 실패를 보면서 질문을 다듬어 왔다. 그래서 개선 효과를 판단하기에는 낙관적이다. 실제로 이 세트에서 87%가 나오던 같은 설정이, 개발 중에 보지 않은 질문 25개에서는 **65%**였다.

별도 작성 세트는 다음 원칙으로 만들었다.
- 현재 스키마 기준으로 범주 필터, NULL 처리, 조인, 서브쿼리, 함정 문항(NULL 그룹, 텍스트로 저장된 숫자)을 고르게 넣는다.
- 정답 SQL은 실제 DB에서 실행해 결과를 확인한 뒤 넣는다.
- **모델 결과를 보고 질문을 고치지 않는다.**
  - 예외 1: H20. 데이터 결함(헤더 행이 데이터로 섞임)이 드러나 정답 기준을 고쳤다. 질문은 그대로 두었다.
  - 예외 2: H19. 실명을 공개 저장소에 두지 않으려고 같은 유형의 질문으로 바꿨다. 바꾼 질문은 0/3이었고, 그대로 반영했다.

## 개선 과정 (별도 작성 세트 기준)

| 단계 | 변경 | 정확도 | 바뀐 문항 |
|---|---|---|---|
| 0 | 기준선 (사고 모드 끔, 재생성 2회, 값 누락 검사) | 65.3% | |
| 1 | 데이터 정리: 반복 헤더·구분선 행 삭제, 숫자 컬럼을 BIGINT로 | 72.0% | H15, H20 |
| 2 | 프롬프트 규칙 3개 추가 (동률·NULL·이상/이하), anti-join 정적 검사 | 80.0% | H09, H10 (+H25 우연히 맞음), **H01 퇴행** |
| 3 | 값 누락 검사 버그 수정, 1055 오류 안내 | 84.0% | H01 회복 (개발용 세트의 C27 퇴행도 회복) |
| 4 | H19 질문 교체 (실명 제거) | 80.0% | H19 0/3 (문항만 다시 돌림) |

### 단계별 메모

**1. 데이터 정리가 가장 확실했다**
- 집계 결과에 `호관`, `---` 같은 가짜 그룹이 나오는 원인을 추적했다. 여러 쪽짜리 PDF 표를 적재하면서 쪽마다 반복되는 헤더와 `|---|` 구분선이 데이터 행으로 들어간 것이었다.
- 같은 이유로 숫자 컬럼에 헤더 글자(예: '연번')가 섞여서 숫자형 추론이 실패했고, TEXT로 저장됐다. 그래서 `'80' > '100'`이 참이 되는 문자열 비교 오답이 생겼다.
- DB를 정리하는 데서 끝내지 않고, **적재 단계에서 반복 헤더와 구분선 행을 빼도록 고쳤다** (`drop_noise_rows`).

**2. 프롬프트 규칙은 효과와 부작용이 함께 왔다**
- 규칙 12("가장 ~"은 `LIMIT 1` 대신 `MAX`/`MIN` 서브쿼리로 동률 포함)로 H09와 H10이 0/3에서 3/3이 됐다.
- 대신 프롬프트가 길어지면서 개발용 세트의 C27이 3/3에서 0/3이 됐다. 규칙을 빼고 다시 돌려 2/3이 나오는 것으로 원인을 확인했다. GROUP BY 오류(1055)를 MySQL 영어 원문만으로는 재생성으로 고치지 못한 것이다.
- 규칙을 되돌리지 않고, 1055 오류에 "이 컬럼을 `MAX()`로 감싸거나 GROUP BY에 넣으라"는 한국어 안내를 붙여 해결했다 (C27 3/3).

**3. 검사 도구 자체의 버그**
- 값 누락 검사가 SQL 전체에서 값을 찾다 보니, 별칭 `정보보호장비_총_개수`에 든 글자를 보고 `종류 = '서버'`로 값이 바뀐 오답을 통과시켰다. 문자열 리터럴 안에서만 찾도록 고쳤다.

## 효과가 없어서 기본에서 뺀 것

| 시도 | 결과 | 판단 |
|---|---|---|
| 사고 모드 (Qwen3 thinking) | 개발용 세트에서 정확도 87.5%(끔: 88.5%), 중앙 지연 75.6초(끔: 8.7초), 600초 타임아웃 1건 | 이득 없이 지연만 9배. 끔 |
| 스키마에 범주형 값 목록과 NULL 개수 싣기 | 별도 세트 65.3% → 70.7%. 하지만 오른 문항(H09, H25)은 목록과 관계없었고, 노린 H08(NULL 그룹)은 못 고쳤다. 개발용 세트에서는 C18이 3/3 → 0/3으로 퇴행했다 (호관 값 목록을 보고 GROUP BY에 호관을 넣음) | 노린 효과가 확인되지 않아 기본 끔 (`--column-hints`로 다시 실험 가능) |
| 스키마에 테이블 행 수 싣기 | 조인 조건을 거꾸로 짜는 오답이 생김 | 되돌림 (`db_builder.py` 주석) |

### 답과 같은 모양의 테이블이 점수를 부풀린 사례
- 개발용 세트의 C27("호관별 단말기 수와 호실 합계를 나란히")은, DB에 그 형태로 미리 만들어 둔 결과 테이블이 있을 때 3/3이었다. 모델이 그 테이블의 컬럼명을 그대로 따라 썼다.
- 그 결과 테이블들(값이 부풀려진 것 포함)을 지우자 0/3이 됐다.
- 점수만 보면 테이블 삭제가 손해였다. 하지만 실제로는 테이블 모양을 베껴 맞힌 것이라 삭제를 유지했다.

## 남은 실패

| 문항 | 유형 | 내용 |
|---|---|---|
| H08 | NULL 처리 | "가장 많이 설치된 날짜"에서 NULL 그룹(7대)을 1위로 냄. 규칙 13으로도 못 고침 |
| H12 | anti-join | 검사가 잘못된 모양을 잡아 `NOT EXISTS`로는 고치지만, "IP가 **적혀 있는**" 조건을 빠뜨림 (단독 실행 2/3, 전체 실행 0/3) |
| H19 | 질문 이해 | "1305호"를 `'305'`로 씀 |
| H06, H13, H25 | 질문 이해 | "월별"을 호관별로 묶음, 없는 컬럼 참조, 2단계 질의를 끝까지 못 짬 |
| C24, C29, C30 | 질문 이해 | 나눗셈 순서를 뒤집음, "서버가 가장 많은 제조사"를 모델별 대수로 셈, 조인 후 호관별 집계를 빠뜨림 |

데이터 정리, 검사, 규칙으로 잡을 수 있는 유형은 거의 다 잡았다. 남은 것은 질문을 SQL 구조로 옮기는 단계의 오류라, 큰 모델이나 비슷한 질문의 예시를 넣는 few-shot이 다음 수단이다.

## 한계

- **표본이 작다.** 25문항 중 20문항 정답의 95% 신뢰구간은 대략 59~93%다.
- **반복 3회의 편차(±0.0%)는 확실성을 뜻하지 않는다.** temperature 0.1에서는 반복해도 거의 같은 SQL이 나오기 때문이다.
- **문항과 정답 SQL을 같은 쪽에서 작성했다.** 질문 해석이 작성자 쪽으로 치우쳤을 수 있다.
- **실제 사용자 질문으로 재지 않았다.** 별도 작성 세트에는 함정 문항이 많아서(25개 중 약 5개), 실제 질문 분포에서의 정확도와는 다를 수 있다.
- **수정·삭제(DML) 쿼리 생성은 평가하지 않았다.** 앱은 실행 전 확인 단계로 이를 막는다.

## 결론

- SQL을 읽을 수 있는 담당자가 **쿼리 초안 도구**로 쓰기에는 충분한 수준이다. 단순 조회, 필터, 집계는 거의 틀리지 않는다.
- SQL을 검증할 수 없는 사용자에게 답을 바로 주기에는 부족하다. 틀린 답의 대부분이 오류 없이 실행되고 그럴듯한 결과를 내기 때문이다.
